# AGENT_ONBOARDING

面向后续 Agent 的最小入口文档：先定位目标，再按需下钻，避免再次被历史信息淹没。

## 0）先读什么（30~90 秒）

1. 先读 [`CONTEXT.md`](../../CONTEXT.md)：确认“当前在做 / 阻塞 / 下一步”。
2. 再按任务类型读取：
   - 需要运行/命令/依赖 -> [`README.md`](../../README.md)
   - 需要模块边界/调用关系 -> [`ARCHITECTURE.md`](../../ARCHITECTURE.md)
   - 需要文档地图/历史材料 -> [`INDEX.md`](./INDEX.md)
   - 需要复用经验/避坑 -> [`LESSONS.md`](./LESSONS.md)
   - 需要清理判断 -> [`CLEANUP_INVENTORY_2026-05-02.md`](./CLEANUP_INVENTORY_2026-05-02.md)
3. 最后再看相关代码与脚本，不先翻历史长文档。

## 1）当前任务怎么确认上下文

按这个顺序确认，避免误判：

1. 任务目标：要交付什么（功能、修复、文档、验证）。
2. 任务边界：允许改哪些文件，不允许改哪些文件。
3. 验收标准：以什么结果算完成（命令、页面现象、脚本输出）。
4. 现状证据：从代码/配置/脚本读取事实，不凭记忆推断。

若目标、边界、验收任一不清晰，先写“假设/待验证”，不要直接进入大范围改动。

## 2）项目主体在哪（优先关注）

- 应用主代码：`src/`
- 静态资源：`public/`
- 自动化与验证脚本：`scripts/`
- 项目文档：`docs/`
- 数据与后端相关目录：`supabase/`
- 当前工作台主体：`workbecnch-ui-2/app-old/`
- 历史工作台原型：`workbench-ui/`
- 旧静态导出产物：`workbecnch-ui-2/deploy2/`

建议：优先读与本任务直接相关的 1~2 个目录，不做全仓库漫游。不要把旧原型或静态导出产物误判为当前主线。

## 3）历史资料在哪（按需查）

历史方案、阶段计划、归档记录主要在 `docs/`，常见命名特征：

- `ARCHIVE_*`
- `*_PLAN_*`
- `*_NOTES_*`
- 带日期后缀（如 `2026-04-27`）

这些材料用于“追溯决策背景”，不应直接当作当前真实状态。清理前的长 `CONTEXT.md` 快照在 `../archive/2026-05/CONTEXT_BEFORE_CLEANUP_2026-05-02.md`。

## 4）清理/废弃内容怎么看

先分类再处理（本文件只定义入口，不直接执行清理）：

1. `运行必需`：当前脚本、配置、被代码引用的文件。
2. `历史参考`：阶段性文档、复盘、方案草稿（可保留但应标注）。
3. `疑似冗余`：旧日志、临时产物、重复文档。

判定原则：

- 有代码/脚本直接引用 -> 视为必需。
- 无引用但有明确历史价值 -> 归档保留。
- 无引用且无说明 -> 列入“待确认清理清单”，由主控统一决策。

## 5）验证命令怎么选（最小必要）

按改动范围选最小验证，不一上来跑全套：

1. 仅文档改动：人工阅读结构与链接是否可用。
2. 类型或接口相关改动：`npm run typecheck`
3. 功能链路改动：按目标选择 `npm run verify:*`（如 `verify:all` 或单项脚本）。
4. 运行态问题：`npm run dev` 或项目约定的 clean 启动命令复现。

执行验证前，先确认命令是否在 `package.json` 的 `scripts` 中存在。
